# vscape_hcim_tracker

Tracks Vidyascape hardcore ironman xp history in PostgreSQL and serves
text and HTML rankings.

> **Disclaimer:** This project is entirely AI-generated by **DeepSeek V4.1
> Flash** (`opencode-go/deepseek-v4.1-flash`) running in the OpenCode agent
> harness. No human wrote the implementation. Review it before use.

## How it works

- `/api/tracker/player/{username}?time=n` returns xp gained over the last `n`
  seconds, so `xp_at(t) = xp_now - gained(now - t)`.
- Backfills everything since 2025-01-26 on a 24h grid, adds a 6h checkpoint per
  run, and rechecks the last 7 days so failed fetches are retried. That epoch is
  the earliest data the API holds.
- Backfill is interval-major: for each timestamp, newest first, every player is
  fetched before moving to the previous timestamp.
- Only accounts whose highscores entry still reports `ironman == 2` (hardcore)
  are recorded.
- Storage is sparse: a `snapshots` row is written only when a skill's xp
  changes. Every fetched timestamp goes into `checkpoints`, so unchanged points
  are not fetched again. Missing xp is treated as the previous value.

## Usage

```sh
cp .env.example .env      # set a real POSTGRES_PASSWORD
docker build -t vscape_hcim_tracker-app:latest .
docker compose up -d --force-recreate
```

- page: <http://localhost:8000/>
- text: `reports/latest.txt`
- logs: `docker compose logs -f collector` or `docker compose logs -f web`
- stop: `docker compose down` keeps the database
- delete data: `docker compose down -v`
- update: `./scripts/update.sh` pulls, rebuilds the image and recreates
  `collector` and `web`; the database container is left running

Three containers: `db` (PostgreSQL with the `pgdata` volume), `collector` (API
to database), and `web` (reports and HTTP on port 8000). Only `web` is
published. The first collector run backfills everything since 2025-01-26, the
earliest data the tracker API holds: about 644 days, 250,000 requests, roughly
17.5 hours at the default 4 req/s. Later runs fetch the current 6h checkpoint
plus retries. Reports regenerate every minute.

`--lookback` defaults to the fixed start epoch, so backfills stay complete as
time passes. Passing a duration still limits the window, but never before
2025-01-26.

Set `POSTGRES_PASSWORD` before the first start. Postgres applies it only when
the `pgdata` volume is initialized. If the password changes later, reset the
database or update the role:

```sh
docker compose down -v    # deletes stored xp
# or, to keep the data:
docker compose exec db psql -U xp_tracker -d xp_tracker \
  -c "ALTER ROLE xp_tracker PASSWORD 'new-password';"
```

`reports/` is bind-mounted. The container entrypoint fixes its ownership to
uid 1000 on startup, so a directory created by Docker as root does not block
report writes.

## Scheduled updates

```sh
./scripts/install-cron.sh
```

Adds one crontab entry that runs `scripts/update.sh` at the start of every
hour and appends the output to `update.log`. Re-running replaces the entry
instead of duplicating it. `./scripts/install-cron.sh --remove` deletes it.
Cron must be installed and the user must be able to run `docker`.

`scripts/update.sh` also writes `version` with the pulled commit hash and the
update time, and copies it to `reports/version`. Reports show it as
`software version <hash>, updated <time> UTC`: a grey right-aligned footer on every
webpage, and the last line of `reports/latest.txt`.

## Backups

```sh
./scripts/backup.sh
```

Writes a compressed custom-format `pg_dump` to `backups/` on the host. The `db`
service must be running. Set `BACKUP_DIR` to use another output directory.

Restore the newest dump in `backups/`:

```sh
./scripts/restore.sh
```

- Copies `backups/` into `/tmp/restore` inside the `db` container.
- Stops `collector` and `web` for the duration, then starts them again.
- Runs `pg_restore --clean --if-exists --no-owner --no-privileges`.
- Prints the restored player and snapshot counts, then removes the staging copy.

Restore a specific dump:

```sh
./scripts/restore.sh backups/xp_tracker_20261101T085521Z.dump
```

Environment overrides:

- `BACKUP_DIR` - source directory, default `backups`.
- `RESTORE_DB` - target database, default `$POSTGRES_DB`.
- `RESTORE_KEEP_SERVICES=1` - leave `collector` and `web` running.

`pg_restore` drops and recreates every object in the target database, so any
data written after the dump is lost.

## API rate limits

No quota is documented and `/api/highscores/player/...` returns no rate-limit
headers. Overlapping requests cause HTTP 503.

- One global limiter covers all workers and retries; `--rate` is total requests
  per second.
- Defaults: `--workers 2 --rate 4`.
- 429, 500, 502, 503 and 504 are retried up to five times with 2, 4, 8 and 16 s
  backoff plus jitter. A `Retry-After` header is honoured.
- Failed checkpoints are retried within the 7-day window.

Eight concurrent requests produced roughly 50% HTTP 503 responses in testing.
Higher concurrency does not lose data, but slows the initial backfill.

## Reports

`reports/latest.txt` and `reports/latest.html` show the top 5 gains per skill
and span (day/week/month/year), plus each player's best window. The page adds
metadata, a coverage bar and a player search box.

Each player gets `reports/players/<name>.html` with current xp and OSRS level, a
checkpoint-coverage bar, separate past/best tables, and 2x2 charts per skill:
total xp line and xp/hour area. The `overall` row shows total level. Sparse data
is treated as constant between stored points.

## Configuration

`config/` holds one file per service:

- `collector.yaml`: `skills`, `account_filter_codes`, API `urls`, and `defaults`
  for `interval_seconds`, `collect_interval_seconds`, `retry_window_seconds`,
  `data_start_epoch`, `workers`, `rate`. Also `priority`: `players`,
  `interval_seconds`, `retention_seconds`, `top`.
- `web.yaml`: `defaults` for `report_interval_seconds`, `top_n`, `base_url`,
  and the `spans` used for xp records.
- `db.yaml`: database fallbacks `host`, `port`, `database`, `user`.

`src/utility.py` loads all three at import (`VSCAPE_HCIM_TRACKER_CONFIG_DIR`
overrides the directory) and provides `build_dsn` and `parse_priority_players`.

## Priority tracking

Priority tracking covers the five players with the highest `overall` xp,
plus any names in `config/collector.yaml` under `priority.players`. Both sets are
fetched every 10 minutes, in addition to the 6h grid. The list ships empty:

```json
"priority": {"players": [], "interval_seconds": 600,
             "retention_seconds": 86400, "top": 5}
```

The collector re-reads the priority list before every fetch and the web every
report cycle, so edits apply without a restart. `config/` is bind-mounted
read-only. `VSCAPE_HCIM_TRACKER_PRIORITY_PLAYERS` or `--priority` overrides it.
High-frequency rows are pruned after 24 hours.

`reports/priority/` contains:

- `index.html` - top players, manual names, and any player still holding
  unpruned high-frequency rows.
- `<name>.html` - one large 24h chart per skill, `hh:mm` ticks, regular snapshot
  data in orange.
- `<name>.xml` - RSS feed, one item per 10-minute fetch with changed xp,
  starting with the time since the last priority or regular snapshot; entries
  are separated by ` | `.

RSS links use `VSCAPE_HCIM_TRACKER_BASE_URL` or `--base-url` (default
`http://localhost:8000`).

## Storage cost

Measured on 75 players with roughly one year of data: 216 bytes per snapshot
row and 111 bytes per checkpoint row, including indexes.

- Per player, full history: about 950 snapshot rows (only xp changes) and 672
  checkpoints (daily backfill since 2025-01-26 plus the retry window).
- Full backfill, 371 players: about 352,000 snapshot rows (~76 MB) and 250,000
  checkpoints (~28 MB); roughly 100 MB of database in total.
- Ongoing 6h collection: `371 × 1,460 = 541,000` checkpoints per year (~60 MB)
  plus about 199,000 snapshot rows per year (~43 MB), so roughly 100 MB/year.
- Checkpoints grow for every player regardless of activity. Snapshots only grow
  with xp changes; a player who never gains xp costs 24 rows in total (one
  baseline per skill).

The Docker volume also holds WAL and preallocated files; at a 16 MB database it
was about 7 times that size.

The player pages are static files, not database rows: measured at about 117 KB
per player on average, so roughly 43 MB for 371 players in
`reports/players/`. They are fully rewritten only when a player's data
changes.

## Notes

- `xp_at(t)` is only as exact as the server's samples; `xp_now` and the gain
  query are separate requests.
- Negative derived xp is clamped to zero.
