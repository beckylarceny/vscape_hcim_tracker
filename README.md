# vscape_hcim_tracker

Tracks Vidyascape hardcore ironman xp history in PostgreSQL and serves
text and HTML rankings.

> **Disclaimer:** This project is entirely AI-generated by **DeepSeek V4.1
> Flash** (`opencode-go/deepseek-v4.1-flash`) running in the OpenCode agent
> harness. No human wrote the implementation. Review it before use.

## How it works

- `/api/tracker/player/{username}?time=n` returns xp gained over the last `n`
  seconds, so `xp_at(t) = xp_now - gained(now - t)`.
- Backfills one year on a 24h grid, adds a 6h checkpoint per run, and rechecks
  the last 7 days so failed fetches are retried. The API history caps at about
  one year.
- Only accounts whose highscores entry still reports `ironman == 2` (hardcore)
  are recorded.
- Storage is sparse: a `snapshots` row is written only when a skill's xp
  changes. Every fetched timestamp goes into `checkpoints`, so unchanged points
  are not fetched again. Missing xp is treated as the previous value.

## Docker

Three containers: `db` (PostgreSQL with the `pgdata` volume), `collector`
(API to database), and `web` (report generation and HTTP serving on port 8000).
Only `web` is exposed.

```sh
cp .env.example .env      # set a real POSTGRES_PASSWORD
docker compose up -d --build
# page:  http://localhost:8000/
# text:  reports/latest.txt
docker compose down       # keeps the database
docker compose down -v    # deletes stored xp
```

The first collector run is the one-year backfill: about 136,000 requests, or
roughly 9.5 hours at the default 4 req/s. Later runs fetch only the current 6h
checkpoint plus retries. Defaults (`--workers 2 --rate 4`) are conservative
because the API returns 503 under concurrent load. Reports are regenerated
every minute by `web`.

## Local usage

```sh
createdb xp_tracker
export VSCAPE_HCIM_TRACKER_DSN=postgresql:///xp_tracker

python -m src --loop                            # collect and report
python -m src --collect-only                    # fetch only
python -m src --serve-only --serve-port 8000    # report and serve only
python -m src --report-only                     # one report, no fetching
```

Key options: `--interval 24h` (backfill step), `--collect-interval 6h`,
`--retry-window 7d`, `--lookback 365d`, `--workers 2`, `--rate 4`,
`--report-interval 1m`, `--top 5`, `--serve-port 0`, `--dsn` or
`$VSCAPE_HCIM_TRACKER_DSN`.

## Reports

Only `reports/latest.txt` and `reports/latest.html` are kept; older report
files are deleted. For each skill and `overall` they show the top 5 gains over
the past day/week/month/year and each player's best window of that length
(players with zero gain are omitted). The page additionally shows metadata and
a data-coverage bar for backfill progress and gaps. Because storage is sparse,
xp between two stored points is treated as constant; windows still have exactly
the nominal span.

## Storage cost

Measured on 75 players with roughly one year of data: 216 bytes per snapshot
row and 111 bytes per checkpoint row, including indexes.

- Per player, first year: about 537 snapshot rows (only xp changes) and 387
  checkpoints (daily backfill plus the retry window).
- Full backfill, 371 players: about 199,000 snapshot rows (~43 MB) and 144,000
  checkpoints (~16 MB); roughly 60-70 MB of database in total.
- Ongoing 6h collection: `371 × 1,460 = 541,000` checkpoints per year (~60 MB)
  plus about 199,000 snapshot rows per year (~43 MB), so roughly 100 MB/year.
- Checkpoints grow for every player regardless of activity. Snapshots only grow
  with xp changes; a player who never gains xp costs 24 rows in total (one
  baseline per skill).

The Docker volume also holds WAL and preallocated files; at a 16 MB database it
was about 7 times that size.

## Notes

- `xp_at(t)` is only as exact as the server's samples; `xp_now` and the gain
  query are separate requests.
- Negative derived xp is clamped to zero.
